# 多模态分支实施与验收计划

状态：待实现。设计依据与行为约定见 [MULTIMODAL_DESIGN.md](MULTIMODAL_DESIGN.md)。

## 阶段 0：当前交付

- 在个人 fork 的 `design/multimodal-context` 分支提交设计和协议示例。
- 保留上游 main，便于对照和选择性跟进修复。
- 不修改插件元数据宣称新版本，不切换正在运行的服务。

## 阶段 1：消息与图片不丢失

新增平台适配、事件日志、媒体存储和最小 AstrBotBridge。暂不接自发插话、长期记忆、私聊、音视频处理或独立 Web 面板。

实施顺序：

1. 用真正的 AstrBot 构建流程验证 hook 顺序、conversation.history 重载、persona、KB、工具与 extra parts；固定 v4.28.2 的适配边界。
2. 监听消息时先记录完整事件，纯图片/纯 @ 也持久化；不改写原始 event.message。
3. 媒体异步抓取，pending 状态即时可见；临时 id 到哈希文件的映射可重启恢复。
4. 先实现明确 @ / 回复 bot 的确定性触发，选择当前消息、引用和同人最近图片。
5. 在真实请求中验证：历史图片留在所属 user 消息，当前图片内容块有且仅有一份。
6. 记录完整生成与发送状态，重复平台事件不触发重复生成。

此阶段的主要替换点是 `message_cache_manager.py` 的实时缓存职责、`image_handler.py` 的 caption 链路和 `platform_ltm_helper.py` 的实时历史依赖。旧模块保留作隔离对照，不在第一步删除全部旧代码。

## 阶段 2：统一上下文所有权

- 房间共享时间线、引用闭包、短批次和请求 snapshot 生效。
- 从“整段历史拼成一个 prompt”迁移到真实 user/assistant/tool 角色。
- 加入按 tokens 和图片成本裁剪；完整工具轮次原子保留。
- 收敛 `context_manager.py`、`reply_chain_utils.py`、`reply_handler.py` 与 `_session_guard.py` 的重叠职责。
- 删除大范围 hook 包装和正则人格重写，前提是桥接集成验证通过。
- 引用/转发有界获取；旧历史导入是明确的迁移功能，不同时查询两套日志拼接。
- 媒体 TTL、配额、请求租约和断电恢复生效。

阶段 2 完成后，核心图片上下文不依赖开启平台 caption 或旧式群 LTM。

## 阶段 3：删除重复判断

- 移除独立图片描述与描述缓存。
- 情绪、质量、疲劳、频率的多重语义评分收敛为可选的统一门控。
- 保留硬冷却、令牌桶、静默时段、名单和发送去重。
- 明确 @ 不门控；自动插话在工具模式下先门控再启动 Agent。
- 移除错字模拟、重复工具提醒；自然语气交给 persona。
- 默认继续关闭主动参与，先完成明确提问的稳定体验。

不要用“删除了多少模块”验收。验收标准是图片和上下文仍完整、触发策略可解释、调用次数减少且不会重复发送。

## 阶段 4：按实际需要扩展

长期记忆、语音、视频、文档、私聊属于独立增量。每项都先确认模型与适配器能力、输入格式和预算，再加入 typed parts 的序列化实现。多模态模型的名字或配置标签不构成支持证明。

## 验收矩阵

“请求层”指经 AstrBot 组装并交给 provider 的最终内容块，不只是内部缓存有图片；“真实场景”使用无敏感信息的测试群和新生成的测试图片。

| 场景 | 必须成立的断言 |
| --- | --- |
| 同条消息含图片并 @ | 请求恰好包含该图片一次，当前内容没有复制两遍 |
| A 发图，3 秒后 A @ 提问 | A 的原图片消息入选；请求有真实图片内容块 |
| A 发图，21 秒后 A @ 提问 | 同上；不依赖 3 秒 caption 等待窗口 |
| A 发图，群里快速插入多条消息，A 再 @ | 在关联时间窗内不因固定少量消息阈值丢图 |
| A、B 各发图，A 再 @ | 图片身份分别保留，优先关联 A；B 的图不冒充 A 的图 |
| A 明确引用 B 的图并 @ | 引用 B 优先于 A 自己的旧图 |
| A 连发两图并问“比较一下” | 两张图保持各自原事件和顺序；不去掉同一图片的必要引用说明 |
| 只有图片、只有 @ | 事件都入日志；明确纯 @ 的小等待窗口仅收同一发送者 |
| 前图未触发回复，后续 @ | 门控拒绝不清除图片，后续仍可选入 |
| 后面补发文字或图片 | 未开始的同人触发可按窗口合并；其他人触发不混为一批 |
| 图片下载慢、失败、过期 | pending 可等待；失败/过期有区别；不说用户没发图 |
| 群引用旧图，超过热关联窗口 | 原图仍在保留期可加载；已过期明确说明 |
| 插件重启后短期内继续问图片 | 事件与托管文件恢复；不依赖进程内 URL 缓存 |
| 多个 bot 账号/平台/群 | room key 隔离，无跨账号、跨群历史或附件串用 |
| 当前核心的历史格式导入 | 文字正常识别；不可恢复的占位图片明确标记缺失 |
| 带 persona / KB / 记忆插件 / MCP 工具 | 人格、检索输入、扩展块、工具 schema 不丢；转录和图片不重复 |
| req.conversation 带旧历史 | 最终请求使用所选转录，不被核心旧历史重载覆盖 |
| 工具多轮 + 平台分段发送 | assistant/tool 角色与 ID 完整；生成全文保存，发送分段另记 |
| 超过文本/图片预算 | 先删背景；核心附件不静默消失；工具轮次不被截断 |
| 下载时清理 / 请求时清理 | pending 和请求租约正确；没有读已删除文件竞态 |
| 重复事件 / 并发 @ / 发送回调重复 | 事件、生成、回调分别去重；顺序可追踪 |
| 请求失败 / 发送前后崩溃 | 用户事件不丢；发送状态可恢复；uncertain 状态不盲目重复发送 |
| 备用模型缺乏图片能力 | 不把纯文本模型当有效图片回退，不偷偷转换为 caption |
| 主动参与关闭/开启 | 关闭时仅确定性触发；开启后门控失败不执行工具或发送内容 |

## 验证层次与发布条件

1. 组件测试覆盖事件去重、候选选择、引用、预算、图片生命周期和状态恢复。
2. 用请求捕获 provider 跑真实 AstrBot Agent 构建链路，检查最终角色、图片数量、人格与工具。不得仅用手工构造 ProviderRequest 证明集成成功。
3. 图片请求的格式与能力在选定模型上实测。断言以请求完整为主，真实问答验证用含不同大字/不同颜色的两张测试图；不能以模型一句“我看到了”作为唯一证据。
4. 在测试群跑端到端并发、重启、引用和分段场景；确认时延、图片 token 成本与磁盘消耗。
5. 通过后提供可回滚版本，切换时关闭同群旧插件。保留旧数据，转录迁移显式执行。

第一版只有完成阶段 1、2 的必要验收才可发布；阶段 3 的删除可分批进行。已有上游引用图片测试通过不代表新图片连续性已经验收。

## 仍需实测确定的事项

- v4.28.2 最终上下文 hook 的精确顺序，以及不包装其他 hook 的扩展保留方式。
- 当前图片模型通过实际 adapter 对历史 image_url 块、data URI、工具和多张图的处理。
- 默认 token/图片数/磁盘配额是否符合真实群聊负载；文档建议不是已测生产容量。
- 框架会话状态镜像如何避免再次保存 base64 和重复转录；不能直接把完整 wire payload 写回 conversation.history。

遇到接口缺口优先缩小首版兼容范围或向 AstrBot 增加明确扩展点，不恢复旧式全局 monkeypatch。
